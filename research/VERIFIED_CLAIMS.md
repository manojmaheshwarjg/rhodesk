## api-contract  (PARTIALLY_CONFIRMED, confidence high)

**Corrected statement:** All four factual details in the claim are accurate as of 2026-09-11, but only the last one is a documentation defect: Rho's own guides state that a v1 deprecation or sunset comes with "at least 15 days' notice" (a floor, not a fixed 15 days), that partner OAuth is Authorization Code with PKCE (S256) issuing access tokens that expire after 15 minutes (expires_in 900) alongside 30-day rolling refresh tokens and a 1-year grant, and that API Access Tokens are capped at 20 active per business and auto-expire after 45 days of inactivity. Those three are simply what the published guides say and nothing in the corpus or the live API contradicts them, so they are not "contradictions of the actual contract." The genuine defect is the fourth item: the Authentication guide's scope table at /docs/v1/auth#scopes lists only accounts:read, transactions:read and statements:read, while the published OpenAPI security scheme and the live public metadata at https://rhoapi.rho.co/.well-known/oauth-protected-resource/mcp/v1 both enumerate five scopes, adding cards:read and invoicing:read.

**Caveats:**
- Framing error, the main reason this is not CONFIRMED: three of the four listed items (15-day notice, PKCE plus 15-minute access tokens, 20-token cap plus 45-day inactivity) are accurate restatements of what the guides say, not places where the guides contradict the contract. I found no source in the corpus or live API that contradicts any of them. Only the scope-table item is an actual contradiction.
- Precision error: the versioning guide says 'at least 15 days' notice', a floor. 'Only 15 days of deprecation notice' is defensible as a criticism of the floor but misquotes the policy as a fixed figure.
- Scoping nuance that keeps the fourth item honest: cards:read and invoicing:read are each documented on their own guide pages (/docs/v1/cards, /docs/v1/invoicing). The omission is specific to the Authentication page's 'scopes available today' table, which is what the claim says. Do not widen it to 'the docs do not document these scopes'.
- Additional substantiated defects the claim does not mention, all verifiable in the same corpus: (1) /docs/v1/getting-started says the release 'covers accounts and transactions' while the reference ships 14 operations across accounts, cards, transactions, statements and invoicing; (2) offline_access is used as a scope throughout the partner-auth guide but appears in neither the auth-page table nor the OpenAPI security scheme; (3) the auth guide cites RFC 7807 for application/problem+json while the OpenAPI overview cites RFC 9457, which obsoletes it; (4) the OpenAPI AccessToken scheme is declared Type: oauth2 with Token URL https://app.rho.co/settings/access-tokens, a browser settings page rather than the real token endpoint https://auth.rho.co/oauth2/token; (5) within partner-auth, the code exchange shows HTTP Basic client auth, the refresh sample shows no client auth at all, and revoke puts client_id/client_secret in the form body.

The server being more permissive than the stated policy is not itself a contradiction in the guide.
- Everything here except the two live HTTP probes and the well-known fetch is Rho's own self-asserted documentation. The 20-token cap, 45-day inactivity expiry and 15-minute OAuth token lifetime were not exercised against production and cannot be independently verified without a real credential.
